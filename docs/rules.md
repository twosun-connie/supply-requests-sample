# 업무 규칙

> 구현의 근거다. 코드가 이 문서와 다르면 코드가 틀린 것이다. 규칙을 바꿀 때는 이 문서를 먼저 고친다.

## 1. 한 줄 설명

구성원이 비품을 신청하고 담당자가 승인·반려하는 사내 도구.

## 2. 용어

| 용어 | 뜻 | 코드의 이름 |
|---|---|---|
| 품목 | 신청할 수 있는 비품 한 종류 | `item` |
| 신청 | 구성원이 품목 하나를 요청한 한 건 | `request` |
| 이력 | 신청의 상태가 바뀐 기록 한 줄 | `request_event` |
| 신청자 | 신청을 만든 사람 | `requester` |
| 담당자 | 신청을 승인·반려하는 사람 | `approver` |

## 3. 데이터 항목

| 대상 | 항목 | 필수 | 형식·범위 | 비고 |
|---|---|---|---|---|
| 품목 | 이름 | O | 1~50자, 중복 없음 | |
| 품목 | 단위 | O | 1~10자, 기본값 "개" | |
| 품목 | 예상 단가 | O | 0 이상의 정수(원), 기본값 0 | 승인 판단용. 실제 구매가가 아니다 |
| 품목 | 사용 여부 | O | 기본값 사용 | 쓰지 않는 품목은 새 신청에서 고를 수 없다 |
| 신청 | 품목 | O | 품목 하나 | |
| 신청 | 수량 | O | 1~999 정수 | |
| 신청 | 사유 | O | 1~200자 | |
| 신청 | 희망 지급일 | | 날짜 | 시스템이 강제하지 않는다 |
| 신청 | 담당자 메모 | | 1~200자 | 반려 사유 또는 메모 |

## 4. 상태 흐름

| 지금 상태 | 동작 | 다음 상태 | 필요한 권한 | 강제 |
|---|---|---|---|---|
| `submitted`(제출) | 승인 | `approved`(승인) | `requests.approve` | 서버 액션 |
| `submitted`(제출) | 반려 | `rejected`(반려) | `requests.approve` | 서버 액션 |

표에 없는 전이는 할 수 없다. 승인 뒤의 구매·지급 처리는 이번 범위가 아니다(§6).

## 5. 업무 규칙

문장 하나가 테스트 하나다.

| 규칙 | 강제 |
|---|---|
| 수량은 1 이상 999 이하의 정수다 | DB 제약, 입력 검증 |
| 사유는 1자 이상 200자 이하다 | DB 제약, 입력 검증 |
| 신청은 제출 상태로만 만들 수 있다 | 정책 |
| 신청자는 제출 상태인 자기 신청만 고칠 수 있다 | 정책 |
| 쓰지 않는 품목은 새 신청에서 고를 수 없다 | 서버 액션 |
| 제출 상태가 아니면 승인·반려할 수 없다 | 서버 액션 |
| 자기 신청은 승인·반려할 수 없다 | 서버 액션 |
| 반려할 때는 사유(1~200자)를 적어야 한다 | 서버 액션 |
| 상태를 바꾸면 이력을 한 줄 남긴다 | 서버 액션 |

강제: `정책`(DB가 막는다), `DB 제약`(check), `서버 액션`(API를 직접 부르면 우회된다. 내부 사용자만 쓰는 도구라 받아들인다).

## 6. 하지 않는 것

- 승인 뒤의 구매 완료·지급 완료 처리.
- 알림 메일, 파일 첨부, 엑셀 내려받기.
- 신청의 삭제. 잘못 만든 신청은 담당자가 반려한다.
