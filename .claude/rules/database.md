# 데이터베이스 규칙 (Supabase Postgres, RLS, RBAC)

이 구조에는 백엔드 서버가 없다. **실제로 막는 곳은 DB의 권한(grant)과 정책(RLS)뿐이다.** 로그인한 사용자는 브라우저에서 Supabase API를 직접 부를 수 있으므로, 화면과 서버 액션의 검사는 편의이고 두 번째 방어선이다.

## 1. 마이그레이션 파일

- 만들기: `pnpm supabase migration new 《이름》`. 파일을 직접 만들지 않는다(시각이 파일 이름에 들어간다).
- 이름: `create_《테이블》`, `add_《테이블》_《열》`, `add_permission_《대상》_《동작》`, `fix_policy_《테이블》`.
- 파일 하나에 논리적 변경 하나. 테이블이 셋 이상이면 테이블 단위로 나눈다.
- 이미 커밋했거나 DB에 적용한 파일은 고치지 않는다. 새 파일로 바로잡는다. 훅이 막는다.
- 파일 하나는 한 묶음(트랜잭션)으로 적용된다. 중간에 실패하면 그 파일 전체가 적용되지 않는다.
- 이름에는 스키마를 붙인다(`public.requests`). 주석으로 왜 이 변경이 필요한지 한 줄 적는다. 주석은 한국어 평서문이다.
- 파일 안의 순서를 지킨다. 정책이 참조하는 테이블은 그 정책보다 **먼저** 만든다. 아직 없는 테이블을 참조하면 적용이 실패한다.
- **쓴 뒤에는 반드시 `pnpm test:db`를 돌린다.** `pnpm check:migrations` 통과는 "금지된 문장이 없다"는 뜻이지 "적용된다"는 뜻이 아니다. 실제로 적용해 보는 것은 DB 테스트다.

## 2. 테이블을 만들 때: 한 파일에 한 묶음

순서는 테이블 → 설명 → 인덱스 → 권한 → RLS → 정책이다. 하나라도 빠지면 `pnpm test`의 구조 검사가 실패한다.

```sql
create table public.requests (
  id            bigint generated by default as identity primary key,
  requester_id  uuid not null references public.profiles(id),
  title         text not null check (char_length(title) between 1 and 100),
  status        public.request_status not null default 'submitted',
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
comment on table public.requests is '신청. 상태 흐름은 docs/rules.md';
create index requests_requester_idx on public.requests (requester_id, created_at desc);

grant select, insert, update on table public.requests to authenticated;
alter table public.requests enable row level security;

create policy "requests: read own or approve" on public.requests
  for select to authenticated
  using (requester_id = (select auth.uid()) or (select public.authorize('requests.approve')));
create policy "requests: insert own" on public.requests
  for insert to authenticated
  with check (requester_id = (select auth.uid()) and status = 'submitted');
create policy "requests: update own submitted" on public.requests
  for update to authenticated
  using (requester_id = (select auth.uid()) and status = 'submitted')
  with check (requester_id = (select auth.uid()) and status = 'submitted');
```

- 권한(grant)을 적는다. Supabase는 `public` 테이블에 자동으로 주던 권한을 없애는 중이다(새 프로젝트 2026-05-30, 기존 프로젝트 2026-10-30). 쓰지 않는 작업의 권한은 주지 않는다.
- 밖에 보이는 식별자가 추측되면 안 되는 테이블은 `id uuid primary key default gen_random_uuid()`를 쓴다.
- 돈은 원 단위 `integer`, 시각은 `timestamptz`, 날짜만 필요하면 `date`.
- 정책이 거르는 열(`requester_id`, `org_id`)과 외래 키 열에 인덱스를 만든다.

## 3. 정책 쓰는 법

| 규칙 | 이유 |
|---|---|
| 작업별로 나눈다. `for all`을 쓰지 않는다 | 작업마다 조건이 다르다 |
| `to authenticated`를 적는다 | 생략하면 로그인하지 않은 요청에도 적용된다 |
| `auth.uid()`, `auth.jwt()`, `authorize()`는 `(select …)`로 감싼다 | 감싸지 않으면 행마다 다시 계산한다. `exists (select 1 from … where …)` 안에서도 감싼다. 캐스트는 `(select auth.uid()::text)`, `(select auth.uid())::text` 둘 다 된다 |
| `update`에는 `using`과 `with check`를 둘 다, **같은 조건으로** 쓴다 | `using`은 바꾸기 전의 행, `with check`는 바꾼 뒤의 행을 본다. 주인 열을 남으로 바꾸는 것을 막는다 |
| 읽기가 아닌 작업에 `(true)`를 쓰지 않는다. `using`에도, `with check`에도 | 누구나 바꿀 수 있게 된다. 읽기의 `using (true)`는 모든 로그인 사용자가 읽어도 되는 표에만 쓴다 |
| `user_metadata`로 판단하지 않는다 | 사용자가 직접 바꿀 수 있는 값이다 |
| 로그인 없이 읽혀야 하는 테이블은 `project.config.json`의 `db.anonReadableTables`에 적는다 | 의도한 공개만 허용한다. 쓰기는 열지 않는다 |
| 뷰는 `with (security_invoker = true)`로 만든다 | 기본값은 만든 사람의 권한으로 읽어 정책을 우회한다 |

정책을 고칠 때는 `drop policy if exists "이름" on public.《테이블》;` 뒤에 새 정책을 만든다. RLS를 끄지 않는다.

## 4. 권한(RBAC)을 더할 때

역할은 `public.app_role`, 권한 코드는 `public.app_permission`(형식 `대상.동작`), 역할×권한 표는 `public.role_permissions`에 있다. 역할은 로그인 토큰의 `user_role`에 들어가고 `public.authorize('권한 코드')`가 읽는다.

1. `docs/permissions.md`의 「역할별 권한」 표에 행을 더한다.
2. 파일 1: enum 값만 더한다. `alter type public.app_permission add value 'requests.approve';`
3. 파일 2: 그 값을 쓴다. `insert into public.role_permissions (role, permission) values ('admin', 'requests.approve');`와 정책.
4. `pnpm test`가 문서의 표와 `role_permissions`가 같은지 확인한다.

- **새 enum 값은 그 값을 더한 파일에서 쓸 수 없다**(`unsafe use of new value`). 반드시 두 파일로 나눈다. `pnpm check:migrations`가 잡는다.
- 역할을 더할 때도 같다: `alter type public.app_role add value '《역할》';`
- 역할 변경은 다음 토큰 갱신 때 반영된다. 바로 반영하려면 다시 로그인한다.
- 첫 관리자는 대시보드 SQL Editor에서 한 번 지정한다(README). 스키마 변경이 아니라 데이터 한 줄이다.

## 5. 바꾸거나 지워야 할 때: 여러 단계로

열 이름 바꾸기·열 지우기·종류 바꾸기는 한 번에 하지 않는다. 운영 중인 앱이 옛 열을 읽고 있기 때문이다.

| 단계 | 하는 일 | 배포 |
|---|---|---|
| 1 | 새 열을 더한다(NULL 허용 또는 기본값) | 마이그레이션 |
| 2 | 옛 열의 값을 새 열로 복사한다(`update … where 새_열 is null`). 옛 열이 `not null`이면 **푼다**(`alter column 옛_열 drop not null`) | 마이그레이션(1단계와 다른 파일) |
| 3 | 코드가 새 열만 읽고 쓰게 바꾼다. DB 테스트의 insert 문도 새 열로 바꾼다 | `db:push` → `db:types` → 앱 배포. 운영에서 확인 |
| 4 | 옛 열을 지운다. 새 열이 필수면 `not null`을 건다. 파일 첫 줄에 `-- destructive-ok: 《왜 지워도 되는지》` | 마이그레이션 |

- 2단계에서 옛 열의 `not null`을 풀지 않으면 3단계에서 새 열만 쓰는 insert가 실패한다.
- 1·2단계는 같은 작업에서 해도 된다. 3단계는 사용자가 `db:push`를 끝낸 뒤에 한다.
- 4단계는 3단계가 운영에 나간 뒤 별도 작업으로 한다. 같은 PR에 넣지 않는다.
- **옮기는 동안 `docs/schema.md`에는 두 열을 모두 적는다.** 옛 열의 뜻에 "제거 예정. 《새 열》로 옮기는 중"이라고 쓴다. 옛 열의 행을 지우는 것은 4단계에서다. 문서는 DB의 지금 모습과 같아야 한다.
- 보고에는 지금 한 단계와 남은 단계를 적는다.
- 표시 주석이 없으면 `pnpm check:migrations`가 막는다. 사유는 한 문장 이상 적는다.
- 같은 검사가 **주민등록번호·여권번호·계좌번호·카드번호 등으로 보이는 열 이름**도 막는다(`security.md` §6). 연락처·주소 같은 개인정보 열은 막지 않고 알린다. 알림이 나오면 그 테이블의 select 정책을 다시 읽는다.
- enum 값은 지울 수 없다. 쓰지 않게 된 값은 그대로 두고 문서에 "쓰지 않음"이라고 적는다.
- `not null`을 더할 때는 기본값을 함께 준다.

## 6. 함수와 트리거 (`db-functions` 확장)

시작 상태에는 `custom_access_token_hook`과 `authorize` 둘만 있다. 더 만들려면 `/add-extension db-functions`로 시작한다.

- 기본은 `security invoker`다. `set search_path = ''`를 적고 본문의 이름에 스키마를 붙인다.
- `public`의 함수는 API로 누구나 부를 수 있다. `security definer`가 꼭 필요하면 `private` 스키마에 만든다.
- 만든 뒤 `revoke execute on function … from anon, public;`을 하고 필요한 역할에만 준다.

## 7. DB 테스트

- 새 테이블마다 `test/db/《테이블》.rls.test.ts`를 쓴다. 본보기는 `test/db/rbac.rls.test.ts`.
- 테이블마다 세 경우를 확인한다: 권한이 있는 사용자, 권한이 없는 사용자, 남의 행. 그리고 로그인하지 않은 요청.
- 정책이 막는 모양은 둘이다. 조건에 맞지 않는 행은 **오류 없이 0행**, 새로 쓰는 행이 `with check`를 어기면 **오류**.
- `test/db/support/`(Supabase 흉내, 구조 검사)는 고치지 않는다. 검사가 실패하면 마이그레이션을 고친다.
- 이 테스트는 메모리 안의 PostgreSQL에서 돈다. 실제 Supabase가 아니다. 확인하지 못하는 것: 대시보드 설정(훅 켜기), API 계층, 실제 로그인. 배포 전에 계정별로 브라우저에서 확인한다.

## 8. 정책으로 막지 못하는 것

- **상태 전이**(`submitted`에서 `approved`로만)는 정책으로 다 표현하지 못한다. `with check`는 바꾼 뒤의 행만 본다.
- **열 단위 제한**(승인자는 `status`만 바꾼다)도 정책으로 막지 못한다.
- 그래서 `with check`로 막을 수 있는 것(바꾼 뒤의 상태 값, 주인 열)은 정책에 넣고, 나머지는 서버 액션이 `rules.ts`로 검사한다. 이 부분은 API를 직접 부르면 우회된다.
- 우회되면 안 되는 규칙이면 트리거로 막는다(`db-functions` 확장). 어느 쪽을 택했는지 `docs/rules.md`의 그 규칙 옆에 적는다.

## 9. 적용

- AI는 DB에 적용하지 않는다. 사용자가 `pnpm db:push`(개발), `pnpm db:push --prod`(운영)를 실행한다.
- 운영 적용 뒤 사용자가 보안 점검을 본다: `pnpm supabase db advisors --project-ref 《운영 Project ID》 --type security`.
- MCP로 DB를 바꾸지 않는다. Supabase MCP는 개발 프로젝트에 읽기 전용으로만 연결한다.
