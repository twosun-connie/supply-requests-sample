# 커밋, 브랜치, PR

형식은 Conventional Commits 1.0.0이다. 기록을 읽는 사람이 제목만 보고 무엇이 달라졌는지 알게 쓴다. 커밋과 푸시는 사용자가 요청했을 때만 한다(`git push`는 사람이 한다).

## 1. 커밋 메시지

```text
종류(범위): 요약

무엇을, 왜 바꿨는가. 어떻게는 코드가 말한다.
결함이면 무엇이 잘못됐고 왜 그랬는지.

Refs: docs/work/2026-09-30-신청-상세.md
```

| 자리 | 규칙 |
|---|---|
| 종류 | `feat` 새 기능 · `fix` 결함 수정 · `docs` 문서만 · `style` 동작이 같은 모양 변경 · `refactor` 동작이 같은 구조 변경 · `perf` 성능 · `test` 테스트만 · `build` 의존성 · `ci` CI 설정 · `chore` 그 밖의 잡일 · `revert` 되돌리기 |
| 범위 | 생략할 수 있다. 화면·영역 이름을 kebab-case로: `requests`, `admin-users`, `auth`, `db`, `ui`, `deps`. 여러 곳이면 생략한다 |
| 요약 | 한국어. 무엇이 달라지는가. 72자 이하(50자 안쪽이 좋다). 마침표 없음. 「수정」「변경」만 쓰지 않는다 |
| 본문 | 제목 다음 줄은 비운다. 한 줄 100자 이하. 제목으로 충분하면 생략한다. `fix`는 원인을 쓴다 |
| 꼬리말 | `Refs: docs/work/《파일》`(작업 기록), `BREAKING CHANGE: 《함께 바꿔야 하는 것》`(제목의 종류 뒤에 `!`), `Co-Authored-By:` |

- 커밋 하나에 목적 하나. 관계없는 정리·포맷 변경을 섞지 않는다. 마이그레이션은 화면 코드와 다른 커밋으로 나눈다.
- 종류는 **사용자에게 달라지는 것**으로 고른다. 기능과 그 테스트를 함께 넣었으면 `feat`다. 동작이 달라지면 `refactor`가 아니다.
- 비밀 값, `.env`의 내용, 개인정보를 메시지에 쓰지 않는다.

```text
좋음  feat(requests): 신청 상세에 승인·반려 버튼 추가
좋음  fix(auth): 공개 경로를 경로 단위로 판정
좋음  docs(schema): requests 의 상태 흐름 설명 보강
나쁨  수정                          ← 종류가 없고 무엇인지 모른다
나쁨  feat: 코드 수정               ← 무엇이 달라지는지 모른다
나쁨  Fix(Requests): 버그를 고쳤다. ← 대문자, 마침표
```

## 2. 브랜치

`종류/짧은-이름`으로 만든다: `feat/request-detail`, `fix/login-redirect`, `docs/schema-comments`. 종류는 커밋과 같고 `hotfix`·`release`를 더 쓴다. 기본 브랜치(`main`)에 직접 커밋하지 않는다.

## 3. PR

- **제목은 커밋 제목과 같은 형식으로 쓴다.** 합칠 때 Squash and merge를 쓰므로 PR 제목이 `main`의 커밋 제목이 된다.
- 본문은 `.github/pull_request_template.md`의 절을 지우지 않고 채운다. 해당 없으면 「없음」. 검증 결과는 실제 출력에서 옮긴다.
- PR 하나에 목적 하나. 생성물을 뺀 변경이 400줄을 넘으면 나눈다(마이그레이션 → 화면).
- 본문은 `/pr-ready`가 쓴다.

## 4. 검사

| 때 | 검사 | 보는 것 |
|---|---|---|
| 커밋할 때 | `.husky/commit-msg` | 커밋 제목·본문의 형식, 브랜치 이름 |
| PR을 열거나 고칠 때 | `pr-format` 워크플로 | PR 제목, 본문의 절, 남은 `《…》` |
| 손으로 | `pnpm check:commit "《메시지》"` | 쓰기 전에 확인 |

막히면 문구의 「다음:」을 따른다. `--no-verify`로 건너뛰지 않는다. 병합·되돌리기처럼 git이 만든 메시지(`Merge …`, `Revert "…"`)는 검사하지 않는다.
