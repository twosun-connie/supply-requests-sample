# 시스템 보강: $ARGUMENTS

실수를 "AI가 못한다"로 끝내지 않는다. **미리 막는 장치가 없었다**로 읽고 장치를 제안한다. 문장으로 부탁하는 것보다 검사로 강제하는 것이 먼저다.

코드를 고치지 않는다. 규칙 파일과 검사 스크립트, 훅, 설정도 고치지 않는다(사람이 관리한다). 제안만 쓴다.

1. **모은다.** `pnpm report:docs`의 「다음에 막을 것」, 최근 작업 기록의 같은 절, 이번 대화에서 사용자가 바로잡은 것.
2. **묶는다.** 같은 원인끼리 묶는다. 한 번만 나온 것은 빼고 「지켜볼 것」에 적는다.
3. **왜 못 막았는지 가른다.**

| 원인 | 뜻 | 먼저 고려할 장치 |
|---|---|---|
| 규칙이 없다 | 어디에도 적혀 있지 않다 | 규칙 문장 + 검사 |
| 규칙이 읽히지 않는다 | 상세 규칙 파일에만 있고 그 파일이 로드되지 않는다 | `AGENTS.md` §4로 올린다. 규칙 파일의 `paths`를 넓힌다 |
| 규칙은 읽혔는데 검사가 없다 | 문장만 있다 | 검사(`scripts/check-*.mjs`), ESLint 규칙, DB 구조 검사 |
| 검사가 있는데 늦다 | 커밋 전이나 CI에서야 걸린다 | 응답을 끝낼 때 도는 `verify:quick`에 넣는다 |
| 문서가 모호하다 | `docs/rules.md`가 두 가지로 읽힌다 | 문서의 문장을 고친다 |
| 사람이 정해야 한다 | 업무 판단이다 | 검사로 막지 않는다. 계획에서 묻게 한다 |

4. **장치를 고른다.** 아래 순서로 가능한 가장 위의 것을 고른다. 아래로 갈수록 덜 지켜진다.
   1. 타입·DB 제약·정책(어길 수 없다)
   2. 검사 스크립트·ESLint·구조 검사(어기면 `pnpm verify`가 실패한다)
   3. 훅(하기 전에 막는다)
   4. `AGENTS.md`의 문장(항상 읽힌다)
   5. 상세 규칙 파일·스킬의 문장(읽어야 지켜진다)
5. **잘못 잡을 것을 본다.** 제안한 검사가 지금의 코드에서 걸리는 곳을 Grep으로 센다. 옳은 코드가 걸리면 조건을 좁힌다. 좁힐 수 없으면 알림(종료 코드 0)으로 낮춘다.
6. **결정 기록을 쓴다.** `pnpm docs:new decision 규칙-보강-《주제》`. 상태는 「제안」. 절마다 아래를 적는다.
   - 배경: 언제 어느 작업에서 몇 번 나왔는가(작업 기록의 파일 이름)
   - 선택지: 장치별 좋은 점과 나쁜 점(잘못 잡을 것, 느려지는 것)
   - 결정: 권하는 장치와 넣을 문장 또는 검사의 조건(정규식, 파일 경로, 실패 문구와 "다음:")
   - 영향: 고칠 파일, 지금의 코드에서 걸리는 곳의 수

## 끝낼 때 출력

```text
제안 《N》건 — docs/decisions/《파일》
사람이 할 일
  1. 제안을 읽고 상태를 「확정」 또는 「폐기」로 바꾼다
  2. 확정한 것은 규칙 파일·검사 스크립트에 반영한다(AI에게 시키려면 파일 수정을 승인한다)
  3. node --test scripts/scripts.test.mjs 와 pnpm verify
지켜볼 것(한 번만 나옴): 《목록》
```
